01

Qué se pone a prueba

Alice y Bruno tienen una sesión sintética y un informe cada uno. La API admite GET /reports/{id} y PATCH /reports/{id}. Ambos modos exigen autenticación; solo el corregido comprueba que el objeto pertenece a la identidad autenticada.

El laboratorio levanta un servidor nuevo en 127.0.0.1 para cada escenario. Un cliente envía HTTP real, registra la respuesta y cierra el servidor al terminar. No hay un objetivo externo ni respuestas simuladas.

Esta es una prueba distinta al laboratorio de herramientas de IA: aquí la frontera evaluada es una API HTTP con dos identidades, lecturas y escrituras.

02

La petición que cruza el límite

La misma sesión de Alice puede consultar su informe 101. Cambiar ese identificador por 202 reproduce el fallo de autorización por objeto en el modo vulnerable:

El marcador SYNTHETIC_BRUNO_202 permite detectar inequívocamente la lectura ajena. Todos los valores y tokens pertenecen a esta demostración; no proceden de usuarios reales.

03

Autorizar el objeto antes de acceder

La identidad proviene del token resuelto por el servidor. El propietario proviene del objeto almacenado. Un campo owner enviado por el cliente o una cabecera que se presente como Bruno no conceden permiso.

Con el parche, la misma solicitud devuelve 404 y el cuerpo {"error":"not_found"}. No incluye nombre, propietario ni marcador del informe ajeno. El objeto inexistente usa el mismo estado y cuerpo.

  • Autorización anterior a la lectura y a la modificación.
  • Rechazo de dos cabeceras de autenticación en la misma solicitud.
  • Solo se admite cambiar el título; el JSON no puede reasignar propietario.
  • Respuestas con Cache-Control: no-store.
04

Comprobar lectura y escritura

44/44 intercambios coinciden con su expectativa. Los 17 escenarios se ejecutan contra ambos modos. En el vulnerable, varios resultados esperados demuestran el fallo; no significan que esa versión sea segura.

Después de cada intento de escritura relevante, el propietario lee su informe. Así se comprueba que la modificación legítima persiste y que una escritura rechazada no altera el estado.

Reproducir y descargar

Ejecutar la misma batería en Docker

El contenedor incluye cliente y servidor; no publica puertos, corre como usuario no root y no necesita red durante la prueba. La imagen base se descarga durante la construcción.

El ZIP contiene API, escenarios, evidencia, instrucciones de exploración manual, Dockerfile y un manifiesto SHA-256. --verify repite la ejecución y compara todo el JSON con la evidencia incluida.

06

Límites de esta evidencia

El servidor y las sesiones son una demostración local de autorización por objeto. No es una API lista para producción: no hay TLS, login, expiración de tokens, base de datos, roles complejos ni control de concurrencia de escrituras.

Los intercambios registrados prueban los escenarios publicados. No constituyen una auditoría de terceros ni demuestran ausencia de cualquier otra vulnerabilidad. El contenedor ejecuta la misma batería y no amplía por sí solo su cobertura.
