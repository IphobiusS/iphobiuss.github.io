01

Alcance y criterio de éxito

Esta aplicación fue construida para demostrar y comprobar un fallo de autorización por objeto. El modo vulnerable contiene el defecto de forma deliberada; este caso no describe un incidente ni un encargo de un cliente.

Alice posee el informe 101 y Bruno, el 202. Cada uno tiene un token sintético. La API admite GET /reports/{id} y PATCH /reports/{id}. La autenticación es la misma en los dos modos; cambia la política que autoriza el objeto.

  • Una identidad válida puede leer y modificar su propio título.
  • La misma identidad no puede leer ni modificar el informe ajeno.
  • Después de un rechazo, el propietario debe recuperar el objeto sin cambios.
  • El control debe funcionar en ambos sentidos: Alice hacia Bruno y Bruno hacia Alice.

Cada escenario inicia un servidor nuevo en 127.0.0.1 y un cliente envía HTTP real. Los datos se reinician entre escenarios y se conservan entre los pasos de cada uno. No hay un destino externo ni respuestas simuladas.

03

Hipótesis y controles que las delimitan

Las siguientes conclusiones se apoyan en los escenarios publicados. Una hipótesis descartada aquí no equivale a descartar esa clase de fallo en cualquier aplicación.

Confirmada
Una sesión válida basta para acceder a un informe ajeno. Las lecturas cruzadas devuelven el marcador del otro propietario y las escrituras cruzadas cambian su título en modo vulnerable. Lectura Alice → Bruno y escritura Bruno → Alice.
Descartada aquí
El fallo depende de entrar sin autenticación. Las solicitudes sin token y con token no reconocido reciben 401 en ambos modos. Los accesos cruzados usan una sesión válida; comprobar la sesión no resuelve la autorización del objeto.
Descartada aquí
Basta con validar los campos del JSON. El JSON inválido y el intento de cambiar owner ya se rechazan en ambos modos. Aun así, un PATCH con un título válido modifica un informe ajeno en modo vulnerable.
Control negativo
Una cabecera del cliente no debe elegir la identidad autorizada. Enviar X-Lab-User: bruno con el token de Alice no abre el informe de Bruno después del parche. Ver petición y rechazo.
Conclusión acotada
Ajeno e inexistente deben responder igual. El estado y el cuerpo del informe ajeno coinciden con los del identificador inexistente después del parche. No se midieron diferencias de tiempo ni canales laterales.
04

Del fallo a su impacto, paso a paso

  1. 1. Establecer dos controles legítimos. Alice lee 101 y Bruno lee 202. Ambos reciben 200 con marcadores distintos. Así se identifica a qué objeto pertenece cada respuesta.
  2. 2. Mantener la sesión y cambiar solo el identificador. Con el token de Alice, GET /reports/202 devuelve el informe de Bruno en el modo vulnerable. La misma petición recibe 404 en el corregido. Comparar los dos modos.
  3. 3. Invertir las identidades. Bruno solicita /reports/101. También obtiene el informe ajeno antes del parche y un rechazo después. Comprobar la dirección opuesta.
  4. 4. Comprobar el impacto de escritura. Alice envía un PATCH válido al informe 202. Bruno lo lee después con su propio token: en modo vulnerable el título cambió; en el corregido conserva su valor inicial. Ver PATCH y lectura posterior.
  5. 5. Conservar la operación permitida. Alice actualiza su propio informe y vuelve a leerlo. El título nuevo persiste en ambos modos: el parche no consiste en desactivar la escritura. Ver el control positivo.

El impacto demostrado es una lectura y una modificación no autorizadas entre dos propietarios del laboratorio. No se asigna una severidad de producción sin el contexto de una aplicación real.

El marcador SYNTHETIC_BRUNO_202 identifica el objeto ajeno de forma inequívoca. Todos los nombres, títulos y tokens son datos públicos inventados para esta prueba.

05

El cambio de código que corrige la causa

Estas dos funciones están en el lab.py descargable y son las políticas que ejecuta la batería. La comparación se genera desde ese archivo al construir esta página. Muestra la diferencia entre los dos modos del laboratorio; no representa el historial de un proyecto ajeno.

El handler resuelve primero la identidad desde el token del servidor y busca el objeto. Después llama a la política seleccionada. Si esta devuelve falso, responde 404 antes de devolver contenido o procesar la modificación. La identidad no procede del JSON ni de X-Lab-User.

En la lectura cruzada, el modo corregido devuelve 404 con {"error":"not_found"}, sin propietario, título ni marcador del informe.

Los controles anteriores al parche se mantienen: una única cabecera de autenticación, un JSON que solo puede cambiar el título y respuestas con Cache-Control: no-store. Ninguno sustituye la comprobación de propietario.

06

Retest: abrir la evidencia de cada escenario

48/48 intercambios coinciden con su expectativa. Los 18 escenarios se ejecutan contra ambos modos. En el vulnerable, varios resultados esperados reproducen el fallo; no significan que esa versión sea segura.

Abre cualquier escenario para comparar petición, cabeceras, estado y cuerpo completo. La flecha une pasos del mismo escenario; en las escrituras, el segundo paso es la lectura de comprobación. Estos controles desplegables funcionan también sin JavaScript.

Las transcripciones proceden del JSON observado. Se omiten el puerto efímero, Host y las cabeceras Date y Server para permitir comparaciones reproducibles. No son una captura de red; el JSON descargable conserva además las expectativas y la huella SHA-256 de cada cuerpo.

07

Reproducir y descargar

Python 3.10 o posterior, sin dependencias. Descarga y descomprime el ZIP; desde su carpeta:

Salida esperada: PASS: 48/48 HTTP checks; complete evidence identical.

Ejecutar la misma batería en Docker

El contenedor incluye cliente y servidor; no publica puertos, corre como usuario no root y no necesita red durante la prueba. La imagen base se descarga durante la construcción.

El ZIP contiene API, escenarios, evidencia, instrucciones de exploración manual, Dockerfile y un manifiesto SHA-256. --verify repite las solicitudes HTTP y compara todo el JSON con la evidencia incluida; una diferencia hace fallar la comprobación.

08

Qué permite concluir y qué queda fuera

Los controles reproducidos respaldan una conclusión concreta: comprobar el propietario antes de leer o escribir bloquea los accesos cruzados ensayados y conserva las operaciones legítimas. Una respuesta de rechazo no basta por sí sola; el retest comprueba también el estado del objeto.

El servidor y las sesiones son una demostración local. No es una API lista para producción: no hay TLS, login, expiración o revocación de tokens, base de datos, roles complejos ni control de concurrencia de escrituras. Tampoco se evaluaron tiempos de respuesta como canal lateral.

La ejecución publicada es automática. Las instrucciones manuales permiten repetirla y explorarla, pero no acreditan una sesión de evaluación humana. Estos escenarios no demuestran ausencia de cualquier otra vulnerabilidad. Docker ejecuta la misma batería y no amplía por sí solo su cobertura.

El siguiente paso técnico sería añadir persistencia y probar carreras entre autorización y escritura, revocación de sesiones y reglas de acceso compartido. Cada ampliación necesitaría nuevas expectativas y evidencia.
