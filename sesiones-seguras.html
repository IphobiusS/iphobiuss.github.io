01

Reconocer un token no basta

Construí esta API local para comparar una sesión conocida con una sesión vigente. El fallo del modo vulnerable es deliberado: no procede de un cliente ni de un incidente real.

Alice y Bruno tienen un portátil y un teléfono cada uno. Sus cuatro tokens iniciales identifican sesiones distintas. GET /me devuelve un marcador propio de cada identidad; las operaciones de sesión se ejecutan mediante POST. Las contraseñas y tokens son públicos y sintéticos.

  • Cerrar sesión debe invalidar ese token, aunque el cliente lo conserve.
  • Cambiar la contraseña debe invalidar las sesiones anteriores de esa identidad, según la política elegida.
  • Revocar un dispositivo debe afectar únicamente a ese dispositivo propio.
  • Una sesión caducada debe rechazarse en la siguiente petición protegida.
  • Las otras identidades y las sesiones que siguen vigentes deben conservar su acceso.

La batería envía HTTP real a 127.0.0.1. Inicia un servidor nuevo por escenario y modo, y mantiene el estado entre pasos. La caducidad usa un reloj controlado dentro del proceso: se prueban las fronteras temporales sin esperar un minuto ni simular las respuestas HTTP.

02

Seguir el token después de cerrar sesión

  1. 1. Confirmar la identidad. El token del portátil de Alice obtiene 200 y el marcador SYNTHETIC_ALICE.
  2. 2. Solicitar el cierre. POST /logout devuelve 200 y signed_out: true en ambos modos. Esa respuesta por sí sola no acredita revocación.
  3. 3. Reutilizar exactamente el token anterior. El modo vulnerable todavía permite GET /me. El corregido devuelve 401 sin identidad ni marcador.
  4. 4. Comprobar el alcance. El teléfono de Alice y el portátil de Bruno siguen obteniendo 200: el cierre afecta a la sesión seleccionada.

Abrir las cinco peticiones y respuestas de Alice. Repetir el control con Bruno.

El retest conserva el token de forma intencional. Borrarlo del cliente impediría observar si el servidor aún lo acepta. En esta API se transporta como Bearer; el caso no ensaya cookies de navegador.

03

Decidir qué debe dejar de funcionar y qué debe continuar

Cierre de sesión
Se marca como revocada la sesión actual. Las demás siguen vigentes. Ver alcance del cierre.
Contraseña
Se exige la contraseña actual y se incrementa la generación de la identidad. Todas sus sesiones previas, incluida la actual, deben dejar de funcionar. El usuario inicia sesión de nuevo; la contraseña anterior se rechaza y la nueva emite una sesión utilizable. Ver los siete pasos.
Dispositivo
El servidor busca su propietario antes de revocarlo. Un identificador ajeno responde igual que uno inexistente y su token sigue funcionando. Ver el rechazo y el control de Bruno.
Caducidad
La vida absoluta es de 60 segundos: a los 59 se permite el acceso; a los 60 se rechaza. Un login posterior obtiene una sesión nueva con su propio límite. Ver el límite inicial y el límite de la sesión nueva.
Orden de ejecución
Un lock protege conjuntamente la validación y la mutación en este proceso. Así una revocación no puede intercalarse entre esos dos pasos. Esto no demuestra coordinación entre réplicas, cachés o bases de datos distribuidas.

Estas son decisiones explícitas del laboratorio. Otra aplicación podría conservar la sesión actual tras un cambio de contraseña, pero tendría que definir y probar esa política. Aquí se eligió invalidarlas todas para que el alcance del cambio sea inequívoco.

04

Validar el estado en cada petición

Este diff se extrae de las funciones que ejecuta el archivo descargable. Ambos modos realizan las mismas mutaciones; la diferencia está en qué estado aceptan al autenticar la siguiente petición.

Un token conocido puede estar revocado, pertenecer a una generación anterior o haber caducado. El modo corregido comprueba las tres condiciones antes de devolver información o realizar otra mutación.

Por ejemplo, una sesión cerrada tampoco puede revocar el teléfono que sigue activo. Ver el intento y la comprobación posterior.

Repetir la ejecución desde el código entregado

Python 3.10 o posterior, sin dependencias. Descomprime el ZIP y ejecuta desde su carpeta:

Salida esperada: PASS: 154/154 HTTP checks; complete evidence identical.

El ZIP incluye código, escenarios con expectativas, resultados, instrucciones, Dockerfile y manifiesto SHA-256. Cualquier diferencia en la evidencia hace fallar la comprobación.

Explorar el cierre manualmente

Inicia el servidor y sigue los comandos de INSTRUCCIONES.txt. En este modo se usa tiempo monotónico real; las sesiones iniciales caducan tras 60 segundos.

La descarga explica cómo repetir con --serve vulnerable, iniciar una sesión nueva y comparar el mismo token antes y después del cierre.

Repetir la batería en Docker

El contenedor ejecuta cliente y servidor como usuario no root, sin publicar puertos. La construcción descarga la imagen base; la ejecución no necesita red externa.

07

Conclusión y límites de la evidencia

La comprobación del estado de sesión bloquea los tokens invalidados en los escenarios publicados. El resultado combina rechazos y controles positivos: también verifica que otras identidades y las sesiones legítimas sigan funcionando.

El servidor es una demostración: HTTP sin TLS, datos en memoria, contraseñas sintéticas en texto plano y tokens deterministas públicos. No implementa rate limiting, cookies, CSRF, refresh tokens, MFA, OIDC ni almacenamiento distribuido. La duración de 60 segundos sirve para la prueba y no es una recomendación universal de configuración.

La prueba automática de caducidad avanza un reloj controlado; no mide precisión temporal, carreras distribuidas ni retrasos de caché. Tampoco acredita una evaluación humana o una auditoría de una aplicación en producción. Docker reproduce la misma cobertura.

Una ampliación posterior podría introducir persistencia y dos réplicas para comprobar revocaciones compartidas. Necesitaría escenarios y evidencia nuevos.
